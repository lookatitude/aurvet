What a signed chain proves, and what it does not

Every entry in chain.log is canonical JSON signed with a detached SSHSIG under chain-entry.aurvet.dev, and each names its predecessor by prev_hash. A verification therefore proves two things about the copy in front of you: every entry was signed by a key you trust, and no entry in the middle was altered or removed.

⚠

It does not prove the copy is complete. Entries removed from the end leave a chain that verifies exactly as it did before: nothing is inconsistent, there is simply less. Truncation is invisible from inside the construction, and no amount of signing changes that.

Closing it requires a length and head recorded somewhere the host cannot retroactively change — an anchor. In practice that is a copy pushed to a remote.

Where the push credentials live

⚠

Push credentials necessarily live on the monitored machine. The host being watched holds the credential that can write to the record of what happened on it. There is no arrangement of local files, permissions or signatures that removes this: a machine that can push can, with the same credential, attempt to rewrite what it pushed.

So the mitigation is not local and cannot be made local. It lives entirely on the remote.

The two load-bearing remote controls

These are security controls, not repository hygiene. If either is missing, the anchor is worth nothing and the tool is reporting confidence it has not earned.

ControlWhat it stopsIf it is absent
Force-push denial (reject non-fast-forward updates) An attacker with the push credential replacing the remote history with a shorter or forked one. The remote can be rewritten to agree with the truncated local copy, and the anchor confirms the attacker’s version.
Branch protection (no deletion, no history rewrite, ideally no direct push outside the appending identity) Deleting the branch and re-creating it, which achieves the same as a force-push by another route. Same outcome, one command further away.
ⓘ

A reader who concludes “the chain is signed, therefore it cannot be altered” has misunderstood the construction. That misunderstanding is exactly the manufactured confidence P4’s ship gate exists to prevent, which is why chain.ReplicationLimitsText is printed with every finding derived from replication state rather than being left in this document.

How the anchor is recorded

aurvet baseline pushed -remote <url#ref> [-protected-remote] writes a signed replication.json beside the chain: schema, remote, confirmed length, confirmed head, confirmation time, and the operator’s assertion that the remote is protected. It is signed under its own namespace, replication.aurvet.dev, so a chain-entry signature can never be replayed as an assertion that something was pushed.

aurvet does not push. It runs no git, holds no credential and opens no socket for this: pushing is your action or your CI’s, and this command records that it happened. -protected-remote is a claim aurvet cannot verify — it is recorded so that its absence is visible in every subsequent report.

Why sign a file the attacker could rewrite anyway?

An attacker holding the signing key can rewrite the anchor. Signing it still buys two things. Without the key, a longer confirmed push cannot be forged at all — the state reads absent, and absent means “nothing is known to be pushed”, the loudest reading. With the key, the only available move is to roll the anchor back, which adds unpushed entries to the report. There is no edit to this file that makes a truncated chain look complete without also producing a critical.

Operating it

# once, on the remote: deny non-fast-forward, protect the branch, no deletions.
# then, after every `baseline init` / `baseline append`:
git -C /var/lib/aurvet/chain push origin HEAD      # your action, your credential
sudo aurvet baseline pushed -remote 'git@host:ops/chain.git#refs/heads/main' \
     -protected-remote -key /path/to/key

aurvet baseline status     # the chain, the unpushed tail, and what was not checked
aurvet baseline verify     # exits 3 when there is no anchor: truncation was NOT checked

Every ordinary aurvet scan prints the unpushed tail first, above the header and behind no flag, because an unpushed tail invalidates the completeness of every statement below it. A machine with no chain prints nothing: an absent chain is not an unpushed one.
