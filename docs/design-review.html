arch-drift — design review

Adversarial review of the approved design, before any code exists. Four review lenses plus independent verification against the target system.

● G-init review 2026-08-04 run-6d9372c5 2 of 4 lenses incomplete

Verdict

The design is rigorous about detection internals — threat model, trust chain, correlation, honesty invariants — and near-silent about everything required to deliver it. That asymmetry is the review's central finding, and the packaging gap you asked about is one instance of it rather than an isolated omission.

Nothing found invalidates the project. But three things previously recorded as verified evidence turned out to be wrong, one proposed subsystem duplicates a tool Arch already ships, and the design as specified would produce roughly 1,860 findings with about 427 criticals and zero actionable results on the machine it was validated against. All are fixable on paper, which is the cheapest place to fix them.

◆

The single most important structural finding: the false-positive gate (INV-8) was defined over PKGBUILDs only. Every one of the largest noise sources lives in system state, not in PKGBUILDs. The release gate is therefore blind to the design's dominant failure mode — it cannot see the very defects this review found by measurement.

S3 · Attack surface, measured against real data verified

Three hazards checked empirically against all 1409 installed packages rather than assumed:

Still open within this area, and not measurable by inspection: TOCTOU between stat and hash, panic-on-malformed-input as denial of the tool, and the privilege-separation question of whether it should run as root at all.

S4 · Static analysis has a hard ceiling, and the design has no state for it verified

Measured across the 34 real PKGBUILDs in the local build cache, rather than reasoned from a hypothetical list of bash tricks. Two results matter more than the rest.

Legitimate PKGBUILDs use eval to generate the functions the tool must analyse. From flutter and flutter-artifacts-google-bin:

eval "package_$_p() {

The split-package functions do not exist in the source text — they are constructed at runtime. This also explains an anomaly in the measurements: zero cached PKGBUILDs match a package_*() definition, despite 433 of 1409 installed packages being split. A static tokeniser cannot see these functions even in principle.

Source URLs are computed, not literal. 10 of 34 (29%) use arch-suffixed arrays such as source_x86_64= — so a parser reading only source= misses the real sources for nearly a third of packages — and 7 of 34 (21%) build URLs through parameter expansion:

source_x86_64=("${pkgbase%-bin}-${pkgver}-${pkgrel}-x86_64.pkg.tar.zst::$url/releases/download/${pkgver/_/-}/…")

Determining the actual host therefore requires variable resolution, not pattern matching.

◆

The missing concept: analysis coverage gaps. The catalog rates eval critical — yet eval appears in 3 of 34 legitimate packages, and the "network fetch" rule produces a 6% false-positive rate on substring matching alone. Flagging these as critical is wrong; staying silent is worse, because the code is genuinely unanalysable. The design needs a third verdict — "could not analyse" — reported under INV-3 exactly as unreadable files are. INV-3 was written for file-read coverage; it must extend to analysis coverage, or every PKGBUILD the tokeniser cannot fully resolve silently reads as clean. That is the same false-clean failure the invariant exists to prevent, arriving through a door nobody was watching.

Adversarial security — self-conducted

Two findings, both material enough to change design decisions.

S1 · Correlation does not survive a competent attacker critical

The catalog's stated core value is that clusters escalate where single signals don't. Splitting signals across two packages is the weak attack. The strong one is simpler: ship the payload as legitimate package content. If a compromised package's build() produces the malicious binary into its own $pkgdir, and the same package ships an ordinary-looking unit for it, then on the installed system:

  • there are no unowned files — every artifact is package-owned;
  • mtree matches perfectly — the digest was generated from that very build;
  • the unit is package-owned, and its ExecStart resolves to a package-owned binary.

Every persistence-surface check goes silent, and so does the integrity tier. This is the blind spot the threat model already names — but its consequence was under-rated: the entire host-side half of the design only catches sloppy malware. The CHAOS RAT packages were detectable because they dropped an unowned binary and wrote a unit from a scriptlet — both avoidable mistakes.

What survives is provenance: off-upstream source host, recent account, maintainer change, tombstone. A second independent argument for the phasing recommendation — and grounds to lower the catalog's severity ratings for surfaces, which currently imply more assurance than they deliver.

S2 · "Rules" is the wrong word and the wrong promise high

Sorting the catalog by what a network-delivered bundle could actually carry:

Expressible as dataRequires compiled logic
Paste-site / IP / shortener host listsExecStart resolution against package ownership
Patterns (curl in build(), base64 -d)Source-host vs. declared-url comparison
Known-bad package names and digestsTombstone corroboration
Thresholds (days since first submission)Correlation clustering and escalation
The third-party-rebuild repo listSymlink resolution, directory exclusion

So all the interesting logic is compiled, and update can only ever ship indicators. That is fine — indicators are what threat intel is. The error is calling it a rules engine, which promises updatable detection capability the design cannot deliver.

✎

Rename it an indicator bundle. State plainly that new detection logic ships with the binary, and drop any implication that update extends what the tool can detect. Combined with the tombstone finding, this makes the intel subsystem smaller and more honest rather than illusory — it simply isn't the thing that answers "discover new threats". The tombstone check is.

The best finding: the AUR publishes an authoritative malware signal verified

Recovered from a crashed reviewer's telemetry and then confirmed by direct fetch. No report surfaced it, and it is the most valuable result of the review.

The design was written on the premise that there is no machine-readable signal for a compromised AUR package. That is half wrong. There is no enumerable list — but there is a per-package authoritative signal, and querying it for packages you already have installed is exactly the use case.

When the AUR removes a package for malware, the git repo remains and carries a tombstone commit stating why:

zen-browser-patched-binHTTP 200history removed due to malware

◆

Two consequences. The highest-severity provenance rule becomes corroborated rather than heuristic: "absent from the index" alone has a real false-positive class, but absent plus a malware tombstone is definitive and needs no curated list. And it further weakens the case for the curated bundle subsystem — the zero-curation live tier is much stronger than the design assumed, reinforcing the recommendation to demote signed-bundle transport to last or never.

Supporting RPC facts, same recovery

  • All 39 foreign packages fit in one batched request (~819-byte URL, HTTP 200). Rate limiting is moot for this workload; per-package polling was never needed.
  • Fields include Maintainer and Submitter — so submitter ≠ maintainer is a directly observable takeover signal the design never used.
  • PackageBase / PackageBaseID are returned, resolving the split-package keying problem (433 of 1409 installed packages are split).
  • Errors are structurally distinguishable from absence — malformed requests return type: "error", genuinely-absent packages return multiinfo with resultcount: 0. This is what makes the "network failure must never read as deleted" rule implementable rather than aspirational.
  • Bulk dumps support range requests; packages.gz is ~544 KB as a cheap existence oracle versus ~13.9 MB for extended metadata.

What the design got wrong

These are corrections, not gaps. Each was recorded in the design as settled, and each is false.

1. The integrity tier duplicates a tool Arch already ships verified

pacman -Qkk already verifies per-file SHA256 against the mtree, already prefixes backup file: for %BACKUP% entries, and already excludes them from its altered-file count. It implements — correctly — the exemption logic the design was going to hand-roll and got wrong:

$ pacman -Qkk pacman vlc
backup file: pacman: /etc/makepkg.conf (SHA256 checksum mismatch)
backup file: pacman: /etc/pacman.conf (SHA256 checksum mismatch)
pacman: 426 total files, 0 altered files
vlc: 349 total files, 0 altered files

The man page understates this — it mentions only permissions, sizes and modification times — but the implementation does full digest verification.

✎

Correction. Stop presenting file-integrity verification as a capability. The novel layer is the one above it: -Qkk trusts the mtree, so it structurally cannot detect mtree tampering — the two-layer baseline can. Reimplement hashing only for the things -Qkk can't do (offline-root, parallelism, structured output, correlation), and say so plainly rather than implying novelty.

2. The pacman hook gates the wrong event verified

The design presented a PreTransaction hook as the catch-all gate. But for an AUR package, makepkg has already run prepare(), build() and package() as the invoking user before pacman sees a built artifact. The build-time-fetch vector — the 2018 acroread compromise — has already fired. The hook cannot see a PKGBUILD at all.

Three further mechanics from alpm-hooks(5), correcting both the design and one review lens:

  • A non-zero exit aborts nothing unless AbortOnFail is set, and that key is PreTransaction-only. The design asserted abort-on-nonzero unconditionally.
  • NeedsTargets passes matched trigger targets — package names for Type=Package, but file paths for Type=Path. Not "always package names".
  • Hooks can be disabled by symlinking to /dev/null, or shadowed by a same-named file in a higher-priority dir. Neither review caught this: an attacker can silently disable a security hook, and the catalog only checks for hooks added, never for legitimate hooks suppressed. That is a live detection gap.
  • PostTransaction hooks do not run if the transaction fails — which matters for the eager-provenance-capture fix below.

3. %VALIDATION% is not an AUR discriminator verified

Recorded as "an exact, free discriminator". Measured distribution is 1371 pgp / 38 none — but there are 39 foreign packages. The outlier is python-pkg_resources: absent from every sync DB, yet %VALIDATION% pgp, packaged by an Arch developer. It was an official repo package that has since been dropped from the repos.

Two consequences, the second more serious than the first:

  • %VALIDATION% must be one weak signal inside a composite, never the discriminator.
  • Dropped-from-repo packages are the primary false positive for the highest-severity provenance rule — "no longer exists upstream". That check would fire on a legitimately Arch-signed package.

Two further breaks, both reported: third-party AUR-rebuild repos (chaotic-aur, Garuda, CachyOS) sign auto-built AUR packages, so on those systems the highest-risk packages read as validated — a false-negative class. And "foreign" is config-dependent: a user with a local repo of their own AUR builds has zero foreign packages while running entirely unreviewed AUR code.

4. %BACKUP% was documented in the wrong file, with the wrong hash verified

The design placed %BACKUP% in desc. Measured: 0 of 1409 desc files contain it; 94 files do, 348 entries, formatted path\t<md5> — MD5, not SHA256. A collector written from the design finds zero exemptions and reports every config drift as critical. This is the direct cause of 19 of the predicted criticals.

5. The *.wants/ rule fires on ordinary system state verified

Rated critical in the catalog. My own measurement of /etc/systemd/system — which differs from the reviewer's numbers but confirms the defect, and exposes a third case neither of us named:

Unowned paths found30Correct treatment
Symlinks resolving to a package-owned unit19Benign — ordinary systemctl enable
*.target.wants directories themselves8Unowned by construction; not units — exclude
Genuinely hand-written unit (+ its enable symlink)1The only real subject

The rule needs three behaviours where it had one: resolve symlink targets, exclude directories, and alert only when the target is unresolvable or not package-owned. A dangling link, or one pointing into /tmp or a home dir, is the real signal — and zero exist here.

6. Static linking conflicts with Arch's Go packaging policy reported

The design mandates CGO_ENABLED=0 and a static binary, justified as "no runtime dependency a compromised system can shim". Arch's Go packaging guidelines mandate -buildmode=pie -linkmode=external, which requires CGO and produces a dynamically-linked binary.

◆

Following Arch convention would silently void a threat-model guarantee — and specifically the one the tool itself checks for. A dynamically-linked arch-drift can be subverted by LD_PRELOAD or /etc/ld.so.preload before it can report on /etc/ld.so.preload, which the catalog rates critical. Also relevant: LD_AUDIT, GLIBC_TUNABLES.

Resolution: deviate deliberately, document it in a PKGBUILD comment, add a test asserting the built binary has no DT_NEEDED, sanitise LD_* and re-exec at startup, and expect namcap warnings you suppress explicitly rather than silence. Secondary trap: GOFLAGS -ldflags is replaced, not merged, by a command-line -ldflags, so naïve version injection silently changes the link mode.

7. Provenance evidence is ephemeral, and degrades silently verified

.BUILDINFO is not retained in the pacman local DB — it exists only inside the .pkg.tar.zst. So pkgbuild_sha256sum, the check tying an installed package to the exact PKGBUILD that built it, works only while the artifact remains in the helper cache. The same applies to the cache git history behind maintainer-change detection.

Measured: 16 of 39 foreign packages (41%) have neither a cache clone nor a retained artifact reported. And 38 of 39 carry %PACKAGER% = Unknown Packager, so there is no local fallback identity. The design's claim that "maintainer-takeover detection works offline, from history already on disk" holds for 59% of packages on the author's own machine.

Compounding it: the yay cache is 88 GB, which is precisely why users clean it.

✎

Two required changes. First, an explicit provenance: unavailable state, counted as a coverage gap under INV-3 — currently those checks simply don't fire and the user reads it as clean, which is the exact failure INV-3 forbids. Second, capture provenance eagerly: record pkgbuild_sha256sum, cache git HEAD, resolved source URLs and upstream commit into the tool's own state at install time — a few KB per package versus 88 GB — so later scans don't depend on a cache users are encouraged to delete. Note that a PostTransaction hook won't fire on a failed transaction, so capture needs a fallback path.

This reorders the build plan. The state layer cannot be third: without it the provenance checks are reliable only on a system that never cleans its cache.

Missing: packaging & distribution

You asked specifically about this. The design contained nothing on it. Findings below are reported except where noted; the local Arch facts they rest on are verified.

The bootstrapping paradox — and no makepkg-compatible signing path

A tool that warns about unvetted AUR packages would itself be installed as an unvetted AUR package. Worse, its own AUR account becomes the highest-value takeover target available, because victims install it with root trust.

A concrete blocker sits underneath: the design's crypto is ed25519 throughout, but makepkg only understands OpenPGP (validpgpkeys plus a signature in source=()). There is currently no mechanism by which an AUR user could verify the release tarball, since the PKGBUILD's own sha256sums arrive through the untrusted channel.

◆

Highest-leverage single action in this review: commit to reproducible builds — pinned Go toolchain, -trimpath, vendored deps, no build-date injection, published SHA256SUMS, CI building on two runners and diffing. It converts "trust me" into "check me", which is the only credible position for this particular tool. Add a second OpenPGP identity purely for release artifacts so validpgpkeys works natively, with the fingerprint published in several independent places.

Two non-obvious defences worth taking: publish the canonical PKGBUILD upstream and have scheduled CI diff the live AUR copy against it — self-defence against takeover of your own package; and register arch-drift, -bin and -git AUR names on day one, or someone else supplies the "convenient binary build" of your security tool.

Reproducibility is silently defeated by defaults verified

OPTIONS=(strip docs !libtool !staticlibs emptydirs zipman purge !debug lto) on this system — strip is on by default. makepkg strips after the build, so the binary inside the package is not the binary you built and signed. Any "verify against the published hash" claim must therefore define reproducibility over the whole .pkg.tar.zst, or set options=('!strip'). Injecting a build date destroys reproducibility outright — use SOURCE_DATE_EPOCH, which makepkg already exports, or omit it.

Key hierarchy and update channel

The design says "embedded ed25519 public key" and stops. Every consequent question is unanswered, and each is exploitable:

AttackWhy the current design permits it
Rollback / freezeNo monotonic version, no expiry → a hostile mirror serves last month's validly signed bundle, the one lacking today's detection. Signature verifies; tool reports clean. INV-3's failure mode delivered through the update channel.
RotationIf the embedded key changes, deployed binaries are stranded, and the fallback behaviour is undefined — fail closed, or keep reporting clean on compiled-in rules?
CompromiseNo revocation, no expiry → a stolen key is valid forever, everywhere.
Suppression bundleNothing prevents a signed bundle that removes detections or whitelists the attacker's package.

Recommended shape, and it stays compatible with the declarative-rules invariant: embed an offline root key set that signs only a delegation document; delegate to short-lived online bundle-signing keys with an expiry; give bundles a monotonic version plus valid_until; refuse versions below a floor held in root-only state; verify signatures over raw bytes before parsing; forbid bundles from introducing keys; and on expiry degrade to coverage-incomplete rather than reporting clean. Report the active rule count so a suspicious drop to near-zero is visible.

File layout and the root-vs-user privilege boundary

Nothing in the design says where anything lives, and that omission hides a privilege-escalation hole: if arch-drift running as root reads a user-writable config that specifies the rules-bundle path, cache location, or public-key path, an unprivileged local attacker controls what a root-privileged security tool trusts.

Rules that follow: when euid==0, never read user config or user cache, and ignore $HOME and SUDO_USER entirely for trust-bearing paths; refuse any config or key file that is group- or world-writable; keep the anti-rollback floor in root-only state, not the cache.

There is also a stated-invariant contradiction: 25 package-owned files are unreadable and 229 directories unlistable as an unprivileged user reported. Since INV-3 makes unreadable files coverage gaps and coverage-incomplete exit 3, an unprivileged scan can never exit 0 — so users will learn to ignore the exit code, which is INV-3's own failure mode. Resolution: scan requires root and refuses unprivileged unless explicitly degraded; baseline hard-refuses unprivileged, because a baseline built without visibility into those 229 directories blesses anything hidden in them forever.

CI, and the corpus licensing trap

INV-8 makes a corpus of real AUR PKGBUILDs a release gate — which as written is non-deterministic (the AUR moves), network-dependent, and legally murky, since most AUR PKGBUILDs state no license.

The clean sidestep: don't store the source text. Pin pkgbase + AUR commit sha + content digest in a lockfile, and assert over a normalised token-stream digest produced by your own tokeniser — which INV-2 requires you to have anyway. That removes the licensing question, keeps the repo small, makes corpus diffs reviewable, and a scheduled refresh job turns corpus drift into a reviewed PR instead of a mystery release failure.

Two hygiene items that are non-negotiable for this project specifically: pin every CI action by commit SHA, not tag — a tool warning about supply-chain compromise while consuming mutable refs will be called out, correctly — and arch-drift's own PKGBUILD must pass arch-drift's own rules as an automated gate. Note that without vendored dependencies, build() performs a network fetch from the Go module proxy, which trips the tool's own critical "network fetch in build()" rule.

Other missing subsystems

Finding fingerprints critical

Suppressions are stored but nothing defines what a fingerprint is. With ~28 pacman transactions/day here, if the fingerprint includes version or rule content every upgrade re-alerts everything; if it includes none, a suppression written for foo-1.0 silently covers a malicious foo-2.0 and the suppression store becomes an attack surface. Needs version-independent identity, explicit scopes, a rule-change epoch, mandatory expiry, and an audit command.

Correlation can't reach the findings that matter high

Correlation is scoped per package — but the whole persistence-surface class is unowned by definition, so there is no package to scope to. The canonical incident cluster requires linking an unowned file back to a package, and only 7 of 39 foreign packages here even have a scriptlet. Needs a temporal-proximity key (all inputs are already collected: mtree time=, %INSTALLDATE%, pacman.log) plus recorded install-time path attribution.

Performance and tiering medium

A stat prefilter reduces 322,594 candidate files to 678 — a 475× reduction — because pacman preserves mtime. But mtime is attacker-controllable, so the fast path is reassurance, not verification. Needs named tiers, full as the default, and a rule that the fast tier unconditionally hashes the security-relevant subset and is never accepted as a baseline basis.

No report history or triage middle ground high

scan prints and exits. The only way to record "I looked, it's fine" is a permanent signed suppression — far too heavy, so users will over-suppress or ignore output. Needs persisted reports, a --since-last diff (the command people will actually run daily, needing no keys at all), and lightweight expiring local acknowledgements distinct from signed adjudications.

Gate reviews one package, risk is the closure high

AUR packages have AUR dependencies; reviewing only the target misses the obvious attack — a benign package pulling a malicious dep. Also unaddressed: split packages (31% of installed packages here) need pkgbase-keyed approval, and -git packages have stable PKGBUILDs with moving sources, so approving once blesses an unbounded stream of future commits. Fix: review the dep closure; record the upstream commit built and diff commit ranges on rebuild.

Concurrency and crash safety medium

No locking anywhere. A scan running while pacman holds db.lck reads a partially written DB and produces spurious findings — and during baseline init that bad state gets signed. Since the design also wants to run from a pacman hook, this is the intended invocation path, not a rare race.

Chain replication is assumed, not verified high

Tamper-evidence rests on a remote the attacker can't rewrite — but push credentials must live on the monitored machine, and nothing detects that the operator simply stopped pushing. Force-push protection is load-bearing and undocumented. Also: the OpenSSH ed25519 key format would let the private key live on a FIDO2 token, satisfying the off-box requirement with hardware instead of discipline.

Observability medium

No way for anyone but the author to debug a false positive. Needs a finding-level explain showing the matched pattern and byte offsets plus the rules that didn't match, and a bug-report bundle that is itself a fixture root — which costs almost nothing because offline-root already exists, and makes every false-positive report a test case.

Smaller items worth recording
  • mtree format hazards beyond escaping: /set and /unset inheritance, float timestamps, ./.-prefixed package metadata that doesn't exist on disk, symlinks with no digest. verified: 237 entries use md5digest rather than sha256, so the parser must handle both.
  • desc fields are not guaranteed present verified — %SIZE% missing on 9 packages, %XDATA% on 6, %LICENSE% on 1. Absent must parse as absent, not error.
  • __pycache__ cannot be blanket-exempted verified — 103 packages ship digest-covered .pyc files; a wholesale exemption is an attacker drop-zone.
  • pacman.log hazards: two different UTC offsets in the same log (DST), entries referring to a different root (-r /mnt), and log rotation — when the log is shorter than the baseline is old, every pre-truncation change becomes an "unexplained" critical. Log coverage must itself be a gap, and an attacker truncating the log should be a finding.
  • The mutable-file exemption list is derivable, not hand-maintained — parse the Target/Exec pairs of installed pacman hooks to compute which files pacman itself regenerates.
  • Filesystem edge cases entirely unaddressed: hardlinks, sparse files (which defeat a size-based prefilter), xattrs and ACLs (not covered by mtree at all — so a setfacl-granted read on a root binary is invisible), btrfs subvolumes, overlayfs, and mid-scan mutation.
  • Multi-user is implicit. Per-user autostart and dotfiles require enumerating users, which INV-4 forbids doing via ambient $HOME — needs an explicit policy, and unreadable or encrypted homes must become coverage gaps.
  • AUR RPC failure policy: network failure must never be interpretable as "package absent from the AUR", which is the highest-severity check. Use the bulk metadata dump rather than per-package RPC.
  • Two changelogs, not one — the rules bundle ships independently of the binary, so it needs its own version line and rationale per change, and reports must name the bundle version that produced a finding.
  • Disclosure must point outward too. When the tool flags a real malicious package, the user holds evidence of an active attack and no instructions. Needs a reporting path to the AUR and Arch security, linked from critical findings — and an in-scope list that explicitly names false negatives as vulnerabilities.

Revised scope

The original phasing was sweep → intel → baseline → gate. On the evidence, that ordering is close to inverted: the intel bundle is a network-facing, key-managing subsystem whose own justification says it will hold a handful of entries per year, while the state layer it scheduled third turns out to be a precondition for provenance working at all.

◆

Recommended first milestone — roughly a fifth of the original scope, independently useful: scan + explain + doctor + --since-last, provenance and integrity only, rules compiled into the binary, no baseline, no signing, no network updates, no install gate. It fully answers question one of the two the project exists to answer, is entirely testable against fixture roots, and needs zero key management.

Then: install gate second — prevention beats detection, and it is the piece that fixes the ephemeral-provenance problem going forward by capturing evidence at install time. Baseline third, and only once fingerprints and the config/privilege model are specified on paper. Intel bundle last or never — its value depends on curation effort that doesn't exist yet, and building signed-bundle transport before there is content for it is pure sequencing risk.

The argument for demoting the baseline is that it is the one subsystem which is actively harmful when half-built: a chain you cannot fully trust manufactures confidence, which is worse than having none.

Decisions needed

  1. Two security questions remain genuinely unexamined — the tool's own attack surface as a root process parsing hostile input, and concrete bash constructs that defeat a static tokeniser. Four attempts at an independent adversarial pass failed (one API crash, two agents that produced nothing). Recommend conducting these inline rather than delegating again.
  2. Accept the reduced first milestone, or keep all four subsystems in scope?
  3. Static vs. Arch-conventional Go build — deliberate documented deviation, or follow the guidelines and drop the anti-preload guarantee?
  4. Distribution posture — source package only, or also a -bin? Reproducible builds as the primary trust story, or OpenPGP release signing, or both?
  5. Does the integrity tier survive at all as an owned capability, now that pacman -Qkk is known to do the file-level work already?

Tooling note — a bug found during this review

Guild's telemetry scrubber (hooks/lib/v1.4/redact-log.ts, group-4 high-entropy rule) is applied to file writes under the wiki directory, where it replaces any run of 20+ characters from [A-Za-z0-9/] with a redaction marker. It silently destroyed three spans of this project's documentation — absolute filesystem paths, and one instance of ordinary English prose containing a slash. Its own source comment documents that relative paths are exempted while absolute ones "keep their existing treatment".

Consequence for this repo: durable design documents live in docs/, which is unaffected. The wiki holds shorter knowledge phrased below the threshold. Guild 2.5.0 is available and may already fix it.
